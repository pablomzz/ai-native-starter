# AI-native SDLC: stages and recommended practices

Research date: 2026-10-30. Labels: [VENDOR] means vendor guidance or vendor-published claim; [INDEPENDENT] means academic study, independent survey or third-party telemetry; [PRACTITIONER] means practitioner or analyst opinion. Several primary pages (dora.dev, arxiv.org, thoughtworks.com) could not be fetched from this session, so some figures come from search snippets or secondary coverage and are marked as such.

## 1. What stages do current AI-native SDLC frameworks describe, and how do they differ from the traditional SDLC?

### Takeaway
The most complete vendor framework (Anthropic's "AI-native SDLC playbook", Aug 2026) keeps familiar stage names (Plan, Design, Build, Test, Deploy, Maintain) but turns them into a loop in which each stage commits a version-controlled artifact (intent.md, spec.md, plan.md, diff + tests, review findings, incident record) that the next stage reads, with human attention moved to approval gates. Spec-driven tools (GitHub Spec Kit, AWS Kiro, Tessl) describe a narrower chain: spec/requirements, design/plan, tasks, implement. The main difference from the traditional SDLC is that writing code is no longer treated as the bottleneck; planning, review, testing and governance are.

### Cited Findings
- [VENDOR] "The AI-native SDLC playbook" by Louis Claxton (Anthropic Applied AI), dated August 21, 2026, ~40 min read, PDF available. Core thesis: "Code is no longer the bottleneck"; approval gates, reviews and handoffs built for human-written code now slow agentic coding; it replaces the linear flow with "a loop in which each accepted artifact fires the next gate." — [Claude blog: The AI-native SDLC playbook](https://claude.com/blog/the-ai-native-sdlc-playbook)
- [VENDOR] Six non-linear stages with "plays" per stage, each listing implementation steps, governance considerations, prerequisites and leading/lagging metrics: — [Claude playbook](https://claude.com/blog/the-ai-native-sdlc-playbook)
  - Plan: capture the idea as `intent.md` (what, why, constraints, open questions); originator brainstorms with Claude; product owner reviews/corrects before commit.
  - Design: Claude turns accepted `intent.md` into `spec.md`, constrained by org-wide skills (brand, security, compliance, UX); flagged concerns go to policy owners.
  - Build: plan mode as default (approved plan committed as `plan.md`: files to change, order, risks, proof of completion); auto mode for low-blast-radius work; short version-controlled `CLAUDE.md`; skills (advisory); hooks as deterministic build-time guardrails; parallel worktree sessions and subagents (start with 2-3 sessions).
  - Test: Claude runs tests/builds/screenshot comparisons on its own work before a human sees it; for bug fixes a failing test is written first and protected from edits; continuous evals in CI using 20-50 real tasks, and each production incident becomes a new eval.
  - Deploy: AI in the PR review loop guided by a `REVIEW.md`; "Findings do not approve PRs. Code owners still do"; hooks as approval gates (allow/ask/block); CI/CD with Claude running non-interactively, able to open PRs but not push to main; production deploys stay behind human release authorization.
  - Maintain: deterministic monitor (sigma bands: 1σ logs, 2σ read-only diagnosis, 3σ may propose action) invokes Claude; Claude writes its diagnosis as a new `intent.md` that re-enters the loop; recurring security scans; Claude in incident channels writing lessons to a version-controlled file.
- [VENDOR] "Every stage commits an artifact the next stage can read"; the commit chain is the audit trail. Principle: "the agent may act up to the production gate and cannot pass it." Separation of duties: the agent that writes code cannot approve it. — [Claude playbook](https://claude.com/blog/the-ai-native-sdlc-playbook)
- [VENDOR] The playbook's adoption order differs from the stage order; each play lists prerequisites, and teams can start with any play that has no dependency. — [Claude playbook (search summary)](https://claude.com/resources/articles/the-ai-native-sdlc-playbook)
- [VENDOR] GitHub Spec Kit workflow: Constitution, then Specify, Plan, Tasks, Implement (with optional clarify and analyze steps), each a slash command; constitution stored in `.specify/memory/constitution.md`; tasks in `specs/<feature>/tasks.md`. GitHub frames Spec Kit as "an experiment" to test how well spec-driven methods work. — [Perficient: Getting started with Spec Kit](https://blogs.perficient.com/getting-started-with-github-spec-kit-installation-and-core-commands/); [CodeMySpec Spec Kit guide 2026](https://codemyspec.com/blog/github-spec-kit-guide); [Xebia, June 2026](https://xebia.com/blog/building-software-with-spec-kit/)
- [VENDOR] AWS Kiro: every spec runs through requirements (`requirements.md`, user stories and acceptance criteria in EARS notation, "WHEN X THE SYSTEM SHALL Y"), design (`design.md`, from codebase analysis plus approved requirements) and tasks (`tasks.md`, trackable list), stored in `.kiro/specs/`. Steering files hold project-wide conventions; agent hooks are event-triggered automations (e.g. update tests on save, scan for leaked credentials). — [Kiro launch blog](https://kiro.dev/blog/introducing-kiro/); [Kiro Quick Spec docs](https://kiro.dev/fr/docs/specs/quick-spec/); [Hora de Codar (secondary)](https://horadecodar.com.br/kiro-spec-driven-development/); [dev.to walkthrough (secondary)](https://dev.to/alizgheib/kiro-from-steering-docs-to-specs-to-hooks-an-agentic-ide-walkthrough-3nbf)
- [PRACTITIONER] Birgitta Böckeler (martinfowler.com, Oct 2025) says the term "spec-driven development" is still in flux; distinguishes three levels: spec-first, spec-anchored (spec kept and evolved), spec-as-source (spec is the only edited artifact, as in Tessl, whose generated files carry "do not edit" headers). Kiro is the lightest (three markdown files), Spec Kit the heaviest (branch per spec, many artifacts). — [Martin Fowler site: Understanding SDD](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html); [fooqux summary](https://fooqux.com/article/226); [Particula comparison](https://particula.tech/blog/spec-driven-development-tools-spec-kit-vs-kiro-vs-tessl)

### Inferences
- Across vendors there is convergence on a written-artifact chain (intent/requirements, spec/design, plan/tasks, code + tests) with a human approval between each; the vendors differ mainly in how heavy the artifacts are and whether the spec stays alive after the code ships.
- Unlike the traditional SDLC (a mostly linear handoff between roles, with line-by-line code review as the main quality gate), AI-native frameworks move human effort to reviewing plans/specs and to deterministic gates, and feed production failures back as new intents/evals (a closed loop).
- This repository's own CLAUDE.md loop (intent, spec, plan mode + plan.md, tests first, reviewer against REVIEW.md, incident + loop entry) maps almost one-to-one onto the Anthropic playbook's plays.

- No independent study compares outcomes of teams using a staged AI-native SDLC versus a traditional one.

## 2. What do vendor guides recommend?

### Takeaway
Vendors agree on: a short, version-controlled context file updated when the agent repeats a mistake; planning before editing; giving the agent a check it can run (tests/typecheck) and asking for evidence; deterministic hooks/deny rules for rules with zero exceptions; a separate reviewer (subagent or review bot) that did not write the code; and tight permissions by default. Anthropic's docs explicitly separate non-deterministic guidance (prompt, CLAUDE.md, skills) from deterministic enforcement (hooks, deny rules, managed settings, tests, CI).

### Cited Findings
- [VENDOR] Claude Code best practices (current docs): two kinds of instructions: non-deterministic (prompt, CLAUDE.md, skills: "there's no guarantee that it'll follow your instructions") and deterministic (hooks, deny rules, managed settings, which the harness "has to execute"). "If something has to happen every time, make it a hook, a deny rule, or a managed setting. CLAUDE.md is for guidelines." — [Claude Code docs: Best practices](https://code.claude.com/docs/en/best-practices)
- [VENDOR] Keep CLAUDE.md short; it is loaded every session so every line costs attention. Include only what Claude cannot work out from code: exact test/typecheck/lint commands, how to run one test file, decisions not in the repo (deploy process, error helper). "If you keep adding emphasis to a CLAUDE.md line and Claude still misses it, that's a sign the line belongs in a hook." Path-specific rules go in `.claude/rules/` with a `paths:` filter; personal prefs in `CLAUDE.local.md`. — [Claude Code docs](https://code.claude.com/docs/en/best-practices)
- [VENDOR] Skills (`.claude/skills/<name>/SKILL.md`) hold team procedures; they are lighter on context than CLAUDE.md because only name/description load until needed; side-effecting workflows should use `disable-model-invocation: true` so only a human can start them. — [Claude Code docs](https://code.claude.com/docs/en/best-practices)
- [VENDOR] Spec before build: ask Claude to "interview me until you could write the spec, then write it to SPEC.md", then start a fresh session to build from it. Write specific prompts that include what "fixed" looks like, e.g. "write a failing test that reproduces it, then fix it." — [Claude Code docs](https://code.claude.com/docs/en/best-practices)
- [VENDOR] Verification: without a runnable check, "you [are] the test suite." Options: say "keep going until they pass" in the prompt, `/goal`, a `Stop` hook (exit code 2 blocks ending the turn), or review by "someone who didn't write the code" (`/code-review` in a fresh subagent). Ask for evidence (command + output), not "All tests pass." When reviewing against a spec, add "skip style": "A reviewer that's asked to find problems will always find something." — [Claude Code docs](https://code.claude.com/docs/en/best-practices)
- [VENDOR] Keep the enforced set of hooks small: "If you ever find yourself at forty of them, most are probably preferences." Auto mode is a classifier, not a hard rule; "never" rules belong in deny rules or hooks. — [Claude Code docs](https://code.claude.com/docs/en/best-practices)
- [VENDOR] OpenAI Codex: AGENTS.md is "an open-format README for agents"; "A short, accurate AGENTS.md is more useful than a long file full of vague rules"; "When Codex makes the same mistake twice, ask it for a retrospective and update AGENTS.md"; layered files (global `~/.codex`, repo, subdirectory); keep approval and sandboxing tight by default; ask Codex to write tests, run checks and review its work before you accept; `/review` command and a `code_review.md` referenced from AGENTS.md; "At OpenAI, Codex reviews 100% of PRs." — [OpenAI Codex best practices](https://developers.openai.com/codex/learn/best-practices)
- [VENDOR] Cursor: project rules in `.cursor/rules` (.mdc, version-controlled), scoped by path, manual, or relevance; keep rules under 500 lines and split into composable rules; AGENTS.md supported as a plain markdown alternative (nested files combine with parents); "when you see Agent make a mistake, update the rule." — [Cursor docs: Rules](https://cursor.com/docs/context/rules); [StackHawk guide](https://www.stackhawk.com/blog/cursor-rules/)
- [VENDOR] Kiro: steering files (project rules), specs (requirements/design/tasks), agent hooks (event-triggered automations). — [Kiro launch blog](https://kiro.dev/blog/introducing-kiro/)
- [VENDOR] GitHub Spec Kit: a "constitution" of non-negotiable project principles that templates are validated against. — [Xebia](https://xebia.com/blog/building-software-with-spec-kit/); [Martin Fowler site](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)

### Inferences
- "Same mistake twice, update the context file" appears independently in OpenAI's and Cursor's docs and in this repo's CLAUDE.md, so it is a cross-vendor norm.
- The clearest shared principle is "advisory vs enforced": context files and skills guide; hooks, deny rules, tests and CI enforce.

- Did not retrieve Google (Gemini CLI / Jules) or GitHub Copilot agent-mode official best-practice pages.
- Kiro official docs pages for hooks and steering were not fetched; details are partly from secondary tutorials.

## 3. What is the evidence or consensus for each practice?

### Takeaway
Consensus is strong across vendors and practitioners for short context files, plan/spec before code, test-based feedback loops, deterministic guardrails, separate review, and human gates, but independent evidence is thin and sometimes cautionary: a 2026 ETH Zurich study found AGENTS.md-style files often lower task success and raise cost, an industrial study found AI review comments mostly acted on but PRs took longer to close, and DORA finds AI amplifies existing practices (small batches, fast feedback, loosely coupled systems) rather than replacing them.

### Cited Findings
- Context files:
  - [INDEPENDENT] Gloaguen et al., "Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?" (arXiv 2602.11988, Feb 2026, ETH Zurich / LogicStar.ai; listed at ICLR 2026): context files tended to reduce task success versus no repository context and raised inference cost by over 20%; human-written files did somewhat better than LLM-generated ones; authors recommend human-written files describe only minimal requirements. Benchmark is Python-only. — [arXiv 2602.11988](https://arxiv.org/abs/2602.11988); [AI Weekly coverage](https://aiweekly.co/alerts/paper-finds-agentsmd-files-hurt-coding-agent-task-success) (from search snippets; full paper not fetched)
  - [INDEPENDENT] A second study, "On the Impact of AGENTS.md Files on the Efficiency of AI Coding Agents" (arXiv 2601.20404, Jan 2026), studies runtime and token use for Codex on GitHub PRs; its results could not be retrieved. — [arXiv 2601.20404](https://arxiv.org/html/2601.20404)
  - [PRACTITIONER] Thoughtworks Radar (vol. 33, Nov 2025, per secondary summary) lists "curated shared instructions for software teams" and AGENTS.md; a non-Thoughtworks 2026 blog cites ~150-200 standing instructions as a rule-of-thumb upper bound (not measured). — [jdinkla summary of Radar 33](https://jdinkla.github.io/software-engineering/2025/11/11/ai-crosses-from-exploration-into-engineering.html)
- Specs before code:
  - [PRACTITIONER] Thoughtworks Radar blip on spec-driven development: workflows begin with a structured functional spec broken into tasks; critique that some tools generate lengthy specs that are hard to review, and that handcrafting detailed rules for AI doesn't scale. One locale page says the blip is not on the current Radar edition. — [Thoughtworks Radar: SDD](https://www.thoughtworks.com/en-in/radar/techniques/spec-driven-development) (search snippet only)
  - [PRACTITIONER] A secondary summary reports Fowler/Böckeler judged current SDD tools ill-suited to many real problems and saw spec-anchored as the pragmatic middle; not confirmed against the original. — [jmlopezdona notes](https://jmlopezdona.github.io/ai-coding-agents-sdd/07-native-sdd-tools/)
- Plan before code / tests first: [VENDOR] recommended by Anthropic (plan mode default, failing test first and protected), OpenAI (write tests, run checks before accepting) and Kiro/Spec Kit (tasks before implement). — [Claude playbook](https://claude.com/blog/the-ai-native-sdlc-playbook); [OpenAI Codex](https://developers.openai.com/codex/learn/best-practices). No independent controlled study found.
- Hooks / guardrails as code: [VENDOR] Anthropic: hooks, deny rules and managed settings are the only deterministic controls; skills are advisory; hooks, skills and settings should be version-controlled and reviewed like code. — [Claude Code docs](https://code.claude.com/docs/en/best-practices); [Claude playbook](https://claude.com/blog/the-ai-native-sdlc-playbook). No independent evidence found.
- AI code review agents:
  - [INDEPENDENT] "Automated Code Review In Practice" (ICSE 2025 SEIP, arXiv 2412.18531), Beko, 238 practitioners, 10 projects: 73.8% of automated review comments resolved, but average PR closure time rose from 5h52m to 8h20m; faulty, unnecessary and irrelevant comments also reported. — [arXiv 2412.18531](https://arxiv.org/abs/2412.18531)
  - [INDEPENDENT] Atlassian study (arXiv 2510.05450, 2025), using a stricter definition (later commit modifies the commented line): 60-70% of LLM-generated comments were not resolved. Definitions differ, so not directly comparable. — [arXiv 2510.05450](https://arxiv.org/abs/2510.05450) (from a search snippet; primary page not fetched)
  - [VENDOR] OpenAI: Codex reviews 100% of PRs internally. — [OpenAI Codex best practices](https://developers.openai.com/codex/learn/best-practices)
- Small PRs / small batches, fast feedback:
  - [INDEPENDENT] DORA 2025 "State of AI-assisted Software Development" (published Sept 23, 2025, ~5,000 respondents): AI is "an amplifier" of strengths and dysfunctions; teams with loosely coupled architectures and fast feedback loops see gains, tightly coupled/slow-process teams see little or none; introduces a DORA AI Capabilities Model of seven practices that amplify AI's impact (list not retrieved). — [Google blog: DORA 2025](https://blog.google/technology/developers/dora-report-2025/); [Google Research listing](https://research.google/pubs/dora-2025-state-of-ai-assisted-software-development-report/); [TechRepublic](https://www.techrepublic.com/article/news-dora-ai-report-2025/)
  - [INDEPENDENT, vendor-telemetry] Faros AI "AI Productivity Paradox" (2025, 10,000 devs / 1,255 teams): high-AI-adoption teams saw PR size +154% and review time +91% (secondary coverage), which argues for keeping PRs small. — [Rob Bowley summary](https://blog.robbowley.net/2025/08/21/new-research-shows-ai-assisted-coding-isnt-moving-delivery/); [Faros research](https://faros.ai/research)
- Human approval gates: [VENDOR] Anthropic: code owners approve, release manager authorizes production, agent cannot push to main; OpenAI: tight approvals/sandbox by default. — [Claude playbook](https://claude.com/blog/the-ai-native-sdlc-playbook); [OpenAI Codex](https://developers.openai.com/codex/learn/best-practices)

### Inferences
- The AGENTS.md study and vendor guidance actually agree on a narrower point: keep context files minimal and human-written; long or generated files can hurt.
- AI review appears to help catch issues but adds review load; pairing it with small PRs and a "skip style / cap nits" policy (the playbook caps nits at five per review) is a reasonable response, though untested.
- Evidence strength ranking (my judgement): small batches/fast feedback (DORA, long-standing) > tests as feedback loop (strong consensus, indirect evidence) > AI review (mixed independent evidence) > context files (mixed, partly negative) > specs-first, hooks-as-code (vendor/practitioner consensus only).

### Gaps
- No independent controlled study found on plan mode, spec-first, or hooks for AI agents.
- DORA's seven AI capabilities and its exact instability numbers could not be fetched (dora.dev blocked from this session).

## 4. What concrete numbers exist (productivity, defect rates, review times)?

### Takeaway
Numbers point in different directions: adoption is near-universal and self-reported gains are high, but controlled and telemetry studies show mixed or negative organizational effects (METR: 19% slower; Faros: review time +91%, bugs per dev +9%), with gains depending on surrounding practices. Most vendor playbooks give metrics to track rather than outcome numbers.

### Cited Findings
- [INDEPENDENT] METR RCT (July 2025, arXiv 2507.09089): 16 experienced open-source developers, 246 tasks in mature repos (~5 years experience each); allowing AI (early-2025 tools) increased completion time by 19%; developers forecast 24% faster and afterwards believed ~20% faster. Authors caution results may not generalize to less experienced developers or unfamiliar code; METR later said newer tools would likely do better. — [Simon Willison on METR](https://simonwillison.net/2025/Jul/12/ai-open-source-productivity/); [arXiv 2507.09089](https://web3.arxiv.org/pdf/2507.09089)
- [INDEPENDENT/VENDOR] Google RCT with 96 Google engineers: AI cut time on a complex enterprise task by about 21% (reported in coverage alongside METR). — [The Decoder](https://the-decoder.com/ai-coding-can-make-developers-slower-even-if-they-feel-faster/)
- [INDEPENDENT] DORA 2025: 90% of respondents use AI at work; 65% rely heavily on it; median ~2 hours/day with AI; AI adoption now linked to higher delivery throughput (a reversal of 2024's finding); only 2 of 7 team archetypes clearly benefit (per a commentator). — [Google blog](https://blog.google/technology/developers/dora-report-2025/); [Rob Bowley on DORA 2025](https://blog.robbowley.net/2025/10/01/dora-2025-ai-assisted-dev-report-some-benefit-most-dont/)
- [INDEPENDENT, vendor-telemetry] Faros AI 2025 (10,000 devs, 1,255 teams): with high AI adoption, PR review time +91%, PR size +154%, bugs per developer +9%; DORA metrics at org level reportedly flat. A subset (~10% of teams with deployment instrumentation) reported bugs per PR +28.7% and incidents per PR +242.7% (different metrics; from secondary sources). Faros's 2026 report covers 22,000 devs / 4,000 teams. — [Rob Bowley summary](https://blog.robbowley.net/2025/08/21/new-research-shows-ai-assisted-coding-isnt-moving-delivery/); [Faros research](https://faros.ai/research)
- [INDEPENDENT] Stack Overflow Developer Survey 2025 (secondary coverage): 46% distrust AI accuracy vs 33% trust, 3% highly trust; 31% use AI agents, 38% don't plan to; 87% concerned about agent accuracy, 81% about security/privacy; among agent users 69% say workflow improved. Figures vary by outlet. — [ShiftMag](https://shiftmag.dev/stack-overflow-survey-2025-ai-5653/); [DevOps.com](https://devops.com/stack-overflow-survey-shows-ai-adoption-for-devs/); [Dice](https://www.dice.com/career-advice/report-developers-are-using-ai-but-dont-totally-trust-it)
- [INDEPENDENT] Automated review at Beko: PR closure 5h52m to 8h20m; 73.8% comments resolved. — [arXiv 2412.18531](https://arxiv.org/abs/2412.18531)
- [INDEPENDENT] AGENTS.md study: >20% higher inference cost with context files. — [arXiv 2602.11988](https://arxiv.org/abs/2602.11988)
- [VENDOR] Anthropic: its monorepo merges grew from ~2,500 to >30,000 a day (mentioned in a related article linked from the playbook, not the playbook itself). The playbook itself gives no customer outcome data, only metrics to track (time to committed intent.md, first-pass merge rate, rework cycles, repeated mistakes CLAUDE.md should catch, eval pass rate, time waiting at gates, DORA measures). — [Claude playbook](https://claude.com/blog/the-ai-native-sdlc-playbook)

### Inferences
- The perception gap (METR) and the review bottleneck (Faros, Beko) are the strongest independent signals; they support the AI-native playbooks' focus on review capacity, small changes and deterministic checks rather than raw code speed.
- Vendor numbers (Anthropic merges/day, OpenAI 100% PR review) describe usage volume, not quality outcomes.

### Gaps
- No independent defect-rate or review-time numbers specifically for teams using the full staged workflow (intent/spec/plan/hooks/evals).
- Primary Faros and Stack Overflow results pages were not fetched; numbers are from secondary coverage and differ slightly between outlets (e.g. trust 33% vs 29%).
- Network access to dora.dev, arxiv.org and thoughtworks.com was blocked in this session; those hosts would need to be allowed to verify exact figures.
