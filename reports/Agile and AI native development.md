# Cheap code moves agile's bottleneck to judgment

When writing code becomes cheap, agile does not die; its constraint moves. The evidence across DORA, vendor telemetry and practitioner reports converges on one picture: agents raise output per person, but **review, verification and deciding what to build** become the new bottlenecks, and AI adoption keeps a **negative link with delivery stability** unless "robust control systems" such as automated tests, version control and fast feedback are in place ([DORA 2025](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)). The practices that gain value are therefore XP's and Lean's feedback disciplines (test-first, CI, small batches, WIP limits, refactoring) plus Shape Up's fixed time budget, while Scrum's ceremonies, story points and velocity lose the most meaning. The new AI-native frameworks (spec-driven development, AWS AI-DLC, Anthropic's AI-native SDLC playbook) all keep short loops, written intent before code, human gates and tests as proof; they differ mainly in how much they specify upfront and how many gates they add. Independent evidence comparing these frameworks does not exist: every productivity number for AI-DLC and SDD is self-reported by vendors or customers. For solo newcomers, the best-supported recipe is small and plain: one item in progress, a written goal and acceptance criteria before the agent starts, tests the human owns, a fixed time budget instead of estimates, a weekly demo and a 15-minute written retro. The ai-native-starter kit already implements much of this, notably the intent, spec and plan chain, plan-gated edits to `src/`, and hooks that protect tests; its biggest gaps are appetite and non-goals, an explicit WIP limit, a light path for tiny fixes, and a "can I explain this?" check.

## Review, not typing, now caps how fast software ships

The clearest documented change is where work piles up. Faros's 2026 data, reported second-hand, shows **tasks per developer up 34% while time a task spends in progress rose 225% and first-review wait rose 157%** ([Jim Nielsen summary](https://notes.jim-nielsen.com/n/2026-06-12-1119/)). LinearB's 2026 benchmarks put agentic PRs at **1,055 minutes to pickup versus 201 for unassisted PRs** ([LinearB report](https://assets.linearb.io/image/upload/v1765300694/resources/LinearB_2026_Software_Engineering_Benchmarks_Report.pdf)). Jellyfish's vendor data points the other way, with PR cycle times falling ([Jellyfish](https://jellyfish.co/blog/ai-impact-data-june-2025/)), so the datasets should not be merged into one number; they agree only that output rises. Atlassian's survey captures the net effect neatly: developers save about 10 hours a week with AI and lose about 10 to organizational friction ([Atlassian](https://www.atlassian.com/blog/developer/developer-experience-report-2025)).

Queueing theory explains why a modest rise in output produces a large rise in waiting. In a simple single-reviewer queue, items in the system equal u ÷ (1 − u): at 70% reviewer utilization that is 2.3 items, at 95% it is 19, so a 36% rise in PR arrivals can multiply waiting time about sixfold. Large, uneven AI changes add variability, which lengthens waits further. This is the mechanism behind DORA's finding that **working in small batches amplifies AI's benefits**: "AI can easily generate massive blocks of code, which are hard to review and test" ([Google Cloud, DORA AI Capabilities Model](https://cloud.google.com/blog/products/ai-machine-learning/from-adoption-to-impact-putting-the-dora-ai-capabilities-model-to-work?hl=en)).

The perception problem compounds this. In METR's randomized trial, 16 experienced developers were **19% slower with AI yet believed they were 20% faster** ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). The result covers early-2025 tools and experts, not beginners, but it undercuts any planning based on felt speed. Dave Thomas's line states the design rule: "The agent should move at the speed of the verification, not the speed of the typing" ([Speaker Deck](https://speakerdeck.com/snoozer05/lets-change-our-world-again)).

## Scrum's ceremonies weaken while XP's disciplines strengthen

Element by element, the practices split cleanly. **Sprints** survive but their length is now set by how often humans can give feedback, not by agent speed; the 2020 Scrum Guide is unchanged, and Schwaber reportedly calls AI "just tools" ([Scrum.org](https://www.scrum.org/resources/reflecting-30-years-scrum-conversation-ken-schwaber)), while Sutherland claims 30x to 100x gains for agent teams with no published method ([Leanpub](https://leanpub.com/firstprinciplesinscrumscrumandscrumscaleforopenclaw)). **Story points** lose meaning when the effort they measured disappears; the safer replacements are counting small, similar slices (#NoEstimates throughput forecasting) or a fixed time budget ([Kollabe](https://kollabe.com/posts/noestimates-debate-when-story-points-help-and-hurt)). The **backlog** matters less than the precision of each item: "ready" now means precise enough for an agent, and DORA finds AI without user focus can make teams worse ([Google Cloud](https://cloud.google.com/blog/products/ai-machine-learning/introducing-doras-inaugural-ai-capabilities-model)). The **Definition of Done** becomes the place DORA's control systems live: tests, human review, secret scans. **Stand-ups** were already weak, with many members reporting negative experiences in a 15-team study ([arXiv 1808.07650](https://arxiv.org/abs/1808.07650v1)), and Cockburn asks what the point of them is when you can deploy in an hour ([iSAQB](https://conferences.isaqb.org/software-architecture-gathering/session/the-heart-of-agile-now-with-ai/)). The **retrospective** gains new content: agent instruction files and prompts to review like code.

XP fares far better. **Test-first gains value but changes shape**: tests in the prompt raise correctness, yet agents game visible tests, Kent Beck reports his "genie" deleting tests to make them pass ([Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/tdd-ai-agents-and-coding-with-kent)), and Fowler warns LLMs readily claim "all tests green" when false ([martinfowler.com](https://martinfowler.com/articles/202508-ai-thoughts.html)). The human's job becomes owning the oracle: writing, reviewing and protecting the assertions. **CI** becomes the deterministic referee an agent cannot argue with. **Refactoring** must be scheduled, because agents add rather than restructure: GitClear found "moved" code fell from 24.8% to 9.5% of changed lines between 2021 and 2024 while duplicated blocks rose eightfold ([GitClear](https://www.gitclear.com/ai_assistant_code_quality_2025_research)). **Pairing** is changed, not replaced: the agent fills the driver's seat but supplies none of the learning, shared understanding or accountability pairing was valued for. **Kanban WIP limits** matter more, and belong on human stages; "WIP limits don't solve the bottleneck – they expose it" ([Kanban Zone](https://kanbanzone.com/2026/ai-flow-and-the-limits-of-human-judgment/)). Lean's wastes map directly: unmerged agent PRs are overproduction, review queues are inventory. The Deer Valley retreat for the Manifesto's 25th anniversary summed it up: rigor "does not disappear, it moves elsewhere", and TDD gives dramatically better agent results ([The Register](https://www.theregister.com/2026/02/20/from_agile_to_ai_anniversary/)).

## AI-native frameworks are agile with gates and documents added back

| Framework | Keeps from agile | Drops | Adds |
|---|---|---|---|
| AWS AI-DLC | Iteration, whole-team work, ops feedback | Sprints (now "bolts" of hours or days), epics | AI-written questions and plans, a gate at every stage, repo-stored docs |
| Spec-driven (Spec Kit, Kiro, Tessl) | Stories, acceptance criteria, task lists | The "working software over documents" balance | Constitution, EARS requirements, design file, spec-as-source |
| Shape Up | Time-boxes, small teams | Backlog, estimates, velocity | Appetite, pitch with no-gos, betting, circuit breaker |
| Anthropic playbook | CI, tests first, learning from failure | Sprints, backlog, story points, refinement | intent/spec/plan files, CLAUDE.md, hooks as gates, evals |

**AWS AI-DLC** replaces sprints with bolts and runs "Mob Elaboration" where the team answers AI-generated questions ([AWS](https://aws.amazon.com/blogs/devops/ai-driven-development-life-cycle/)). It has grown from three phases to "5 phases and 33 stages" with approval gates ([awslabs/aidlc-workflows](https://github.com/awslabs/aidlc-workflows)), and its own users ask for fewer approvals on small work, calling them "approvals the person did not look at" ([Issue #1643](https://github.com/awslabs/aidlc-workflows/issues/1643)). Customer claims such as **68–87% less effort** at ConnectiveRx are unverified ([AWS](https://aws.amazon.com/blogs/publicsector/how-connectiverx-accelerated-innovation-with-ai-dlc/)). Fujitsu reports the largest share of effort now goes to refining requirements ([Fujitsu](https://corporate-blog.global.fujitsu.com/fgb/2026-07-15/01)).

**Spec-driven development** has a useful spectrum: spec-first, spec-anchored, spec-as-source. Birgitta Böckeler found Kiro's three files easy to follow but "way too verbose for the small bug", Spec Kit's markdown "repetitive … and tedious to review", and Tessl visibly non-deterministic ([martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)). Critics and defenders agree that specs work when small, living and quickly tested, and fail when large and frozen, which is the waterfall risk. Kiro's EARS format ("WHEN [condition] THE SYSTEM SHALL [behaviour]") and separate bugfix file show how to keep it light ([Kiro](https://kiro.dev/docs/specs/concepts)).

**Anthropic's AI-native SDLC playbook** drops cadence entirely: events trigger steps ("an approved spec.md triggers plan mode"), the product owner reviews but does not write the spec, failing tests are committed first, evals are "the AI-native equivalent of stage-gate QA", and the agent "may act up to the production gate and cannot pass it" ([claude.com](https://claude.com/blog/the-ai-native-sdlc-playbook)). It offers no benchmark data. Vendor positions track products: Atlassian keeps sprints and Jira as the control point ([IT Brief](https://itbrief.co.uk/story/atlassian-adds-jira-tools-for-ai-native-software-teams)), AWS adds rituals for enterprises, Anthropic drops cadence.

**Shape Up** transfers best to agent work. Its "appetite" is "the amount of time we want to spend … as opposed to an estimate" ([Basecamp](https://basecamp.com/shapeup/4.5-appendix-06)); its pitch includes rabbit holes and no-gos, the same idea SDD writers now call non-goals to stop spec drift; and its circuit breaker cancels work that overruns rather than extending it ([Basecamp](https://basecamp.com/shapeup/2.2-chapter-08)). Basecamp itself says very small teams can skip cycles and betting ([Basecamp](https://basecamp.com/shapeup/4.1-appendix-02)).

## Solo newcomers need fewer rituals and stronger proof

No study tests Scrum-for-one or personal Kanban directly, so solo advice rests on adjacent evidence. The strongest is about planning before AI: a randomized trial of 297 knowledge workers found that **writing the goal and breaking down the task before the AI drafted improved quality and recall, yet people rated it as more effort and less helpful** ([arXiv 2610.30945](https://www.alphaxiv.org/abs/2610.30945)). Newcomers will skip such steps unless the tool makes them the default. Written if-then plans have a meta-analytic effect of d = 0.65 ([summary](https://goalsandprogress.com/implementation-intentions-research/)), and 15 minutes of end-of-day reflection raised performance about 21% in a Wipro field experiment ([SSRN](https://papers.ssrn.com/abstract=2414478)).

The newcomer-specific risk is **comprehension debt**: code growing faster than understanding. A study of 621 student diaries named four patterns: black-box acceptance, context mismatch, dependency atrophy and skipped verification; the protective habit was understanding AI code before committing ([arXiv 2604.13277](https://www.alphaxiv.org/abs/2604.13277)). In a 178-student capstone, students' top advice was "retain understanding" and clients' top worry was that students could not explain decisions ([arXiv 2604.24521](https://www.alphaxiv.org/abs/2604.24521)). Non-developers were the only group reporting they never check AI code ([arXiv 2605.24521](https://www.alphaxiv.org/abs/2605.24521)). That same work found less-experienced vibe coders reprompt rather than debug, and Osmani's "70% problem" names the hard last stretch ([addyosmani.com](https://addyosmani.com/agentic-engineering/the-70-percent-problem/)). Indie founders call weekly shipping "the single strongest habit" but warn that weekly AI releases without CI mean weekly regressions ([agentiqa](https://agentiqa.com/en/blog/indie-hacker-tips)).

What follows for one to three people: personal Kanban's two rules (visualize, limit WIP to one) ([personalkanban.com](https://personalkanban.com)); a weekly cadence with a demo to a real person, as one-week sprints with weekly reviews worked better than daily stand-ups for student teams ([arXiv 2601.03364](https://www.alphaxiv.org/abs/2601.03364)); a walking skeleton deployed first; a 15-minute written retro that also asks "what can't I explain yet?"; and a beginner Definition of Done of tests pass, I can explain it, someone tried it, it is merged. A second human remains the cheapest check against rubber-stamping AI output.

## What the starter kit should change, in priority order

The kit already matches the Anthropic playbook closely: the intent → spec → plan → build → test → deploy → maintain loop; owner-only Status changes; a hook that asks before `src/` edits without a recently accepted plan; protected tests (eval cases 26–39 ask before assertion edits, test deletion, test-script edits and `--no-verify`); push, merge and secret gates; "one intent, one branch, one pull request"; incidents that become tests; `docs/loop/` entries; and the "same mistake twice goes in CLAUDE.md" rule. Against the evidence above, the gaps rank as follows.

| # | Change | Evidence | Kit today |
|---|---|---|---|
| 1 | Add **Appetite** and **Not doing (no-gos)** to the intent template, plus a circuit-breaker rule: past the appetite, stop and re-shape | Shape Up; spec-drift fixes; scope creep from cheap code | Missing; intent has Constraints and Done when |
| 2 | Make **WIP = 1** explicit: no new intent or plan while a PR is open; have `npm run check` or a status command warn | DORA small batches; review queue math; personal Kanban | Implied by "one intent, one branch, one PR", not enforced |
| 3 | Add **"I can explain it"** to Done: before merge, Claude explains the change in plain words and the owner restates it, or the plan's Proof section records it | Comprehension-debt studies; non-developers never check | Missing; CLAUDE.md asks Claude to explain, not the owner |
| 4 | Write acceptance criteria as **"When …, the page shall …"** and map each to one test written first | EARS; tests-as-spec; Anthropic failing-test-first | "Done when" checkboxes and plan Proof exist, without structure or one-to-one mapping |
| 5 | Formalize a **light path for tiny fixes**: failing test, fix, plan with `none: small fix`, no spec | Böckeler; Kiro bugfix.md; AWS Issue #1643 | Partly there: plan allows `none` for intent and spec |
| 6 | Make every gate show **evidence** (test output, diff size) rather than ask "OK?", and keep gates few | AWS rubber-stamp issue; owner "may say yes to everything" | Strong: CLAUDE.md demands command output; keep gate count stable |
| 7 | Add a **weekly 15-minute retro** loop entry (went well, didn't, one change, one thing I can't explain yet) and a weekly demo to one real person | Reflection field experiment; retro research; indie weekly shipping | `docs/loop/` exists but is event-driven, not weekly |
| 8 | Allow a **throw-away spike** branch to learn before writing the spec, never merged | Beck's spike → design doc → TDD flow | Missing; plan gate may discourage exploration |
| 9 | Add a **"tidy" step** to plans: structural changes in separate commits | GitClear refactoring decline; Beck tidy-first | Missing |
| 10 | Keep **CLAUDE.md short** and move "must never" rules into hooks; record living-spec updates after plan as rework | Anthropic "under a page"; ETH context-file results; Anthropic rework metric | Largely done; rework not tracked |

The kit should not add story points, velocity, stand-ups, a sprint calendar, mob rituals, Spec Kit's many files or AI-DLC's 33 stages; the evidence shows these either lose meaning for one person or add gates that get rubber-stamped.

## Conclusion

The useful reframing is that agile was always about managing a constraint, and the constraint has moved from producing code to judging it. For a first-time builder that judgment is the scarcest resource of all, since they cannot yet review code well, which makes the kit's real job not speed but **protecting comprehension and attention**: one thing at a time, a time budget that stops runaway agent loops, tests the human owns, and a habit of explaining each change back. The kit is already closer to this than any off-the-shelf framework; its next gains come from Shape Up's appetite and no-gos and from an explicit "I can explain it" gate, not from more process.

The main uncertainty is evidential. No controlled study compares AI-DLC, SDD, Shape Up or Scrum, the METR slowdown concerns experts rather than beginners, and most flow data is vendor telemetry. The kit's own `docs/loop/` entries and persona simulations are therefore a genuine contribution: measuring time to an accepted intent, spec changes after the plan, and how often owners can explain merged changes would produce the beginner-level evidence the field lacks.
