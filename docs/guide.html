Why a loop?

AI can now write code in minutes. So the slow part of making software is no longer typing code. The slow parts are deciding what to build, checking that it works, and fixing it when real people use it.

An AI-native project handles this with a loop of six stages: Plan, Design, Build, Test, Deploy, Maintain. Claude does most of the work inside each stage. You stand above the loop: you start it, you steer it, and you approve what moves forward.

Here is the chain of files you will make on every lap:

StageYou saveIn the starter
1 PlanAn intent: the problem, in your wordsdocs/intent/
2 DesignA spec: what it must do and howdocs/spec/
3 BuildA plan, then the codedocs/plan/, src/
4 TestTests that prove it workstests/, evals/
5 DeployA pull request with its reviewGitHub
6 MaintainAn incident note and what you learneddocs/incidents/, docs/loop/

Words you will meet

You do not need to memorise these. Come back here when a word is new.

Terminal
A window where you type commands. On Mac it is called Terminal; on Windows, use the Git Bash app (installed with Git).
Git
A tool that saves snapshots of your folder, so you can see every change and undo any of them.
Repository (repo)
A project folder that Git is tracking.
Commit
One saved snapshot, with a short message saying what changed.
Branch
A side copy where you try a change without touching the main version.
GitHub
A website that stores your repo online, so it is backed up and can be shared.
Pull request (PR)
A request to bring a branch into the main version. It is where the review happens.
Claude Code
Claude working inside your project folder: it can read files, run commands and edit code, with your permission.
Plan mode
A Claude Code mode where Claude can read and plan, but cannot change files until you accept the plan.
CLAUDE.md
A one-page note Claude reads at the start of every session: your commands, rules and known mistakes.
Skill
A short rulebook Claude applies when a task matches, such as "write in plain language".
Agent
A helper Claude can send off with one job, such as reviewing a change. It reports back.
Hook
A tiny script that runs before Claude acts. It can block a mistake or ask you first.
Test and eval
A check that runs by itself and fails if something is wrong. Evals here test the hooks.
CI
Short for continuous integration: GitHub runs your checks on every push.
Placeholder
A blank like {{PROJECT_NAME}} that you replace with your own value.

Set up in eight steps

Do this once per project. Copy each command with its button, paste it into your terminal, and press Enter.

  1. Install the tools

    Install Git and Node.js (the LTS version). Make a free GitHub account. Then install Claude Code by following its setup page. You need a Claude plan that includes Claude Code.

    git --version
node --version
claude --version

    Each command should print a version number. If one says "not found", reinstall that tool and open a new terminal.

  2. Unzip the starter and rename it

    Unzip ai-native-starter.zip into a place you will find again, like a Projects folder. Rename the folder to your project's name, for example study-planner.

  3. Open a terminal in that folder

    cd ~/Projects/study-planner

    cd means "change directory". Change the path to where your folder is.

  4. Fill in the placeholders

    npm run init

    It asks seven short questions: the project name, your name (or every owner, if friends are building with you), your time zone, the main branch, what you will build with, and a word from your deploy command. Press Enter to keep a suggestion.

    The stack question
    What will you build with?
  1. Plain web page (HTML, CSS, JavaScript) - the easiest start
  2. Python - install Python 3 and run: python -m pip install pytest ruff
  3. Node.js program (JavaScript in the terminal)
  4. Something else - I will type my own commands
Pick a number [1]:

    Not sure? Pick 1. The starter then adds a tiny working page and one test, so your project runs from the first minute. You can change any answer later in project.config.json.

  5. Run the checks

    npm run check
    What you should see
    ✓ docs chain: ok
✓ guardrail evals: 21/21 passed
✓ secrets: none found
! placeholders: 5 left (ADD_YOUR_OWN_CONVENTION, ...)
  These are yours to write when you are ready.

all checks passed

    The placeholders left are rules only you can write, like a house style. Fill them in as you learn what your project needs. Now see your project run:

    npm run test
npm run start

    npm run test should say fail 0. npm run start opens your page (or runs your program). You now have a working loop before writing a single line yourself.

  6. Make your first commit

    git init -b main
git add .
git commit -m "chore: start from the AI-native starter"

  7. Put it on GitHub

    On github.com, choose New repository, give it the same name, keep it empty, and create it. GitHub then shows two lines that start with git remote add and git push. Copy and run them. From now on, every push runs your checks on GitHub too.

  8. Meet Claude in your project

    claude
    Then type
    Read CLAUDE.md and README.md. In five bullet points, explain how we will work in this project. Then tell me which file I should open first.

    If Claude's answer matches the six stages above, your setup works.

You are set up when

The example we follow

Every stage below uses one running example: Sam, who just finished school, builds a study planner. Sam types study sessions (subject and minutes), and the page shows the minutes per subject this week.

All of Sam's real files are in the starter under examples/study-planner/. Open them next to this guide. Copy their shape, not their words.

01

Plan

An idea becomes a short file in your own words, before anyone writes code.

Capture the idea as an intent

An intent says what is wrong today, who feels it, and what better looks like. You talk; Claude asks questions and writes it up; you fix what it got wrong. Only you can mark it Accepted.

Traditional

An idea sits in a backlog, goes through meetings and story points, and changes owners before anyone builds it.

AI-native

You brainstorm with Claude and save the result as intent.md the same day. It is readable by you and by the next stage.

You need
An idea, or something that annoys you. Nothing else.
Starter helps with
docs/intent/TEMPLATE.md, the write-intent skill, npm run new -- intent <name>

Do this

  1. Make a branch for the idea: git switch -c weekly-minutes.
  2. Tell Claude the problem in your own words. No special language is needed.
  3. Answer its questions. The write-intent skill asks at most three.
  4. Read the draft. Correct anything Claude misunderstood.
  5. Accept it with npm run accept -- docs/intent/251102-weekly-minutes.md (use your file's name). It writes the Status line for you, with today's date and your name. Then commit.
Try it: Sam's prompt
I never know how much time I study each subject. Before exams I find out I barely touched chemistry. Help me write an intent.
What it looks like: docs/intent/251102-weekly-minutes.md
# Intent: weekly minutes per subject
Author: Sam

## Problem
I study for five subjects, but I only remember the ones I like.
I have no quick way to see where my time went this week.

## Outcome
I type each study session (subject and minutes), and the page shows
the total minutes per subject for this week, biggest first.

## Constraints
- No account and no server: everything stays on my laptop.

## Status
Accepted 251102 by Sam

You are done when

Practice to level up

First lap

Write an intent for one tiny wish: "show today's date at the top of the page".

Second lap

Ask a friend what bugs them about how they study. Write their intent in their words.

Stretch

Write two intents for the same problem with different outcomes. Reject one, with a reason in its Status.

02

Design

The accepted intent becomes requirements and a design in one session, with your rules applied as it is written.

Turn the intent into a spec

A spec lists what the change must do, numbered so later stages can point at each item. Claude writes it with your skills switched on, such as security-basics, and lists every concern a skill raises. You settle each concern before any code exists.

Traditional

One team writes requirements, another team turns them into a design, and problems show up in a review weeks later.

AI-native

One session with Claude produces both, guided by your skills, with concerns flagged up front.

You need
An intent whose Status is Accepted.
Starter helps with
docs/spec/TEMPLATE.md, the skills in .claude/skills/

Do this

  1. Run npm run new -- spec weekly-minutes. Use the same short name as the intent: the new spec then links to it by itself, even if you wrote the intent on another day.
  2. Give Claude the prompt below.
  3. Check the spec against your intent: does it solve the problem you wrote?
  4. Answer each flagged concern first. Write down what you decided.
  5. Accept it with npm run accept -- docs/spec/<file> and commit it next to the intent. The command refuses if the intent is not Accepted yet.
Try it
Read docs/intent/251102-weekly-minutes.md and fill in docs/spec/251102-weekly-minutes.md. Apply the skills in .claude/skills. Number each requirement. List every concern a skill raises under "Flagged concerns" and ask me about each one before you finish.
What it looks like: a flagged concern
## Flagged concerns
- Concern (security-basics): localStorage is readable by anyone who
  uses the same laptop. Resolved: Sam is fine with it; the data is
  not private. Written down so a later change does not add private
  data here.

You are done when

Practice to level up

First lap

Ask Claude for a quick sketch of the screen as plain HTML, and link it in the spec's Design section.

Second lap

Write your own skill: copy plain-language and turn it into my-style with your colours and tone.

Stretch

Ask: "What would make this spec fail for a phone user?" Add what you learn as requirements.

03

Build

Nothing is built without an accepted plan. What you know goes into files Claude reads, and the safety rules run as code.

Start in plan mode

In Claude Code, press Shift+Tab until the bottom of the screen says plan mode. The first press usually switches on auto-accept instead, so keep pressing and read the label. Claude can now read everything but change nothing. It writes a plan; you question it; you accept it. Then Claude builds, often in one pass.

Traditional

A developer reads the design, decides the details alone, and writes every line by hand.

AI-native

Claude proposes a plan you can question before any code exists, then writes the code and tests from it.

You need
An accepted spec, and CLAUDE.md filled in.
Starter helps with
docs/plan/TEMPLATE.md; the plan-before-code hook, which asks you before Claude edits src/ while no plan is Accepted

Do this

  1. Switch to plan mode and give Claude the prompt below.
  2. Question the plan: what could this break, which step is riskiest, what did you choose not to do?
  3. Keep going until someone who never saw the chat could build from the plan alone.
  4. Run npm run new -- plan weekly-minutes, ask Claude to put the plan in it, then npm run accept -- docs/plan/<file> and commit.
  5. Leave plan mode and say "Build it, following the plan". If the work drifts from the plan, update the plan. After the merge, run npm run done -- docs/plan/<file>: an accepted plan unlocks src/ for 14 days, so close it when the work is finished.
Try it
Read the intent and spec for weekly-minutes. Write an implementation plan from docs/plan/TEMPLATE.md: the files that change, in order, the risks, and the tests that will prove it works. Write the tests first.
What it looks like: the plan
## Files that change, in order
1. tests/planner.test.js (new): fails at first.
2. src/planner.js (new): until the tests pass.
3. src/index.html (new): the form and the list.

## Risks
- Riskiest step: the week boundary. A session on Sunday night
  must count for that week, not the next.

## Proof
- A Sunday 23:30 session counts in the week that started Monday.

Teach Claude with CLAUDE.md, skills and hooks

Three files carry what you know, so you never repeat yourself:

  • CLAUDE.md holds your commands, conventions and mistakes. One rule matters most: when Claude makes the same mistake twice, add the fix under "Mistakes Claude made twice". Keep it under a page.
  • Skills hold rules Claude must apply the same way every time. A skill is advice, so Claude usually follows it.
  • Hooks are rules that must always hold. The starter has four: they block secrets, protect files like .env, ask before code without a recent plan, and ask before you push or merge to main. Claude must also ask before it edits the hooks themselves, so it cannot quietly switch them off when you say "stop asking me".

You are done when

Practice to level up

First lap

Try editing src/ with no plan. Watch the hook ask you. Say no, and write the plan.

Second lap

Use the researcher agent: "Use the researcher agent to find where the week starts."

Stretch

Add a line to "Mistakes Claude made twice" the next time Claude repeats an error. Check it is gone in the next session.

04

Test

Checks run all the time, not only at the end. Claude can see them pass or fail, and fixes its own work.

Give Claude a feedback loop

A test is a small program that checks one thing and fails loudly if it is wrong. When Claude can run the tests, it notices its own mistakes and fixes them before you ever see them. Your job is to decide what "working" means.

Traditional

Testing is a separate phase at the end, done by another team, and problems come back days later.

AI-native

Tests are written first and run after every change. Evals check the safety rules themselves.

You need
A test command. npm run init set one for your stack: node --test for web and Node.js, python -m pytest for Python.
Starter helps with
npm run test, npm run check, the verifier agent, 21 guardrail evals in evals/cases/

Do this

  1. Ask for the tests first, and watch them fail: that proves they test something.
  2. Let Claude build until they pass.
  3. Before you call it done, ask the verifier agent to run every check.
  4. Never let anyone, including Claude, change a test just to make it pass. Fix the code instead.
Try it
Use the verifier agent to run lint, tests, build and npm run check. Show me the results as a table. If anything fails, fix the code, not the test, and run it again.
What it looks like: one test
test('Sunday 23:30 counts in the week that started the Monday before', () => {
  const sunday = new Date(2025, 10, 9, 23, 30);
  const list = addSession([], { subject: 'History', minutes: 20, at: sunday });
  assert.deepEqual(weeklyTotals(list, TODAY), [{ subject: 'History', minutes: 20 }]);
});

Evals work the same way for your safety rules. Each one feeds a hook a pretend action and checks the answer. They come in twins: one action the hook must stop, and a close one it must allow. That way a hook cannot "pass" by blocking everything.

You are done when

Practice to level up

First lap

Run node --test examples/study-planner/code/planner.test.js. Then break one line in planner.js and watch a test fail.

Second lap

Ask Claude: "What input would break this? Write a test for it." Keep the tests that fail.

Stretch

Write a new eval twin in evals/cases/ for a command you never want Claude to run.

05

Deploy

An AI review goes first, and you decide. Approvals that must never be skipped are hooks, not habits.

Review, then ship with a gate

You push your branch and open a pull request on GitHub. The reviewer agent reads the change against REVIEW.md and the plan, and lists findings. You fix the "must fix" items, then merge. Pushing to main always asks you first, because a hook says so.

Traditional

A person reads every line, and rules get checked in meetings, sometimes and not always the same way.

AI-native

Agents review every change the same way. People review what matters most, and hooks enforce the approvals.

You need
Passing tests and a GitHub repo.
Starter helps with
REVIEW.md, the reviewer agent, the PR template, CI in .github/workflows/ci.yml, the ask-before-shipping hook

Do this

  1. Ask the reviewer to check your branch (prompt below).
  2. Fix each "must fix". Run the reviewer again until it has no findings.
  3. Push the branch: git push -u origin weekly-minutes. Open a pull request; the template asks for your three file links.
  4. Wait for CI to go green on GitHub. Merge the pull request there.
Try it
Use the reviewer agent to review this branch against REVIEW.md and docs/plan/251102-weekly-minutes.md. List findings, most serious first, and mark each "must fix" or "nice to have".
What it looks like: a finding
1. Must fix (REVIEW.md item 3, security-basics). src/index.html line 41
   builds the list with innerHTML and the subject name. A subject like
   <img src=x onerror=alert(1)> would run as code. Use textContent,
   as the spec says.

You are done when

Practice to level up

First lap

Ask Claude to run git push origin main. Watch the hook ask you, and say no.

Second lap

Add a rule to REVIEW.md that fits your project, such as "every button has a label". Run the reviewer again.

Stretch

Put your page online for free with GitHub Pages, and add the deploy word to askBeforeCommands.

06

Maintain

When something breaks, it becomes a test, a lesson and a new intent. That closes the loop.

Close the loop

Real people will use your project in ways you never expected. Something will break, and that is normal. What matters is that it can never break the same way again. Each problem leaves behind three things: a test, a lesson and, if needed, a new intent.

Traditional

People watch for bugs, fix them in a hurry, and the same kind of bug comes back later.

AI-native

Every problem is written down, gets a guardrail, and feeds back into the loop as a new intent.

You need
Something that broke, or a user who was confused.
Starter helps with
docs/incidents/TEMPLATE.md, docs/loop/TEMPLATE.md, evals/README.md

Do this

  1. Stop the harm first: undo the change, or fix the data.
  2. Run npm run new -- incident <name> and write what happened, in plain words, with no blame.
  3. Add the test or eval that would have caught it. Watch it fail, then fix the code.
  4. Add a loop entry: npm run new -- loop <name>. If the lesson is a rule, put it in CLAUDE.md too.
  5. Close the incident once the guardrail is merged: npm run close -- docs/incidents/<file>.
  6. If the problem shows a real need, write a new intent. A new lap begins.
Try it: what Sam said
My friend typed "1h" in Minutes and the totals now show NaN. Help me write an incident from docs/incidents/TEMPLATE.md, add a test that fails on this, fix the code, and draft a loop entry with npm run new -- loop nan-from-hours.
What it looks like: docs/loop/251109-nan-from-hours.md
# Loop: NaN from "1h" in Minutes

## Tried
The first release, used by two friends.

## Saw
"1h" was saved as NaN and spread to the totals.

## Changed
A test for text in Minutes, and a CLAUDE.md rule: "Check numbers with

## Open

Your second lap, and help

You have finished one lap when an idea has gone from intent to merged code, and you have written down what you learned. Your second lap starts from 08-next-intent.md, or from your own loop log. Each lap gets faster, because CLAUDE.md, your skills and your tests remember what the last lap taught.

Building with a friend

  • When npm run init asks for your name, list every owner: Ana, Bruno. Any owner can accept a document; npm run accept uses your git name.
  • Give each idea its own branch, named after its intent, and merge through pull requests on GitHub. Nobody pushes straight to main; the hook asks either way.
  • Loop entries are one small file each, so two people adding lessons on different branches never get a merge conflict.
  • Agree who reviews whose pull request. The reviewer agent goes first; a person decides.

When something goes wrong

"npm: command not found"

Node.js is not installed, or your terminal opened before it was. Install the LTS version from nodejs.org, then close the terminal and open a new one.

Claude keeps asking before it edits my code

That is the plan-before-code hook. It asks unless a plan in docs/plan/ was accepted in the last 14 days. Write and accept a plan for this change, or say yes for a tiny fix.

Claude asks before editing .claude/settings.json or the hooks

That is on purpose. Those files are your guardrails. Say yes only if you asked for that change and understand it. To change a rule yourself, edit project.config.json by hand.

The check says a Status line "is not valid"

Do not type Status lines by hand. Run the command the message suggests, such as npm run accept -- docs/intent/<file>. It writes the exact format with today's date.

The check says a spec's intent "does not exist"

The path under ## Intent has the wrong date or name. The message suggests the right file ("Did you mean ..."). Copy that path in. Making specs and plans with npm run new and the same short name avoids this.

npm run start does nothing on my computer

Open src/index.html in your browser by hand: double-click it in your file explorer. For Python, check that python --version works; on some computers the command is python3, so change it in project.config.json.

npm run check says a date is after today

The date in a file name must not be in the future. Use npm run new to make files; it uses today's date in your time zone.

The check says a heading is missing

Each document needs the headings from its TEMPLATE.md, written exactly, like ## Status. The message names the template to compare with.

I want to change a rule or a command later

Edit project.config.json for commands, protected files and gated commands. Edit CLAUDE.md for everything Claude should know. Commit both like code.
